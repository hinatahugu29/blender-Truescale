## 実測結果（2026-09-18）

### M-01. 型紙作成は速い。U-02の「面数が主因」説は否定された
cProfile計測（Cylinder相当、ループ数192の小メッシュ）:

    型紙を作成/更新 : 0.058 秒

- _show_generated_from_top   0.013s
- _pattern_delete_generated_for_source 0.004s
- _build_flat_mesh           0.002s
- _calc_real_scale           0.002s

- _pack_islands              0.001s

→ 面数比例のコードはすべて誤差レベル。U-02に書いた「面数が最大の容疑者」は
  少なくともこの規模では成立しない。ユーザ報告は「Cylinderでも重い」。

### M-02. 他アドオンの depsgraph ハンドラが発火する（後に主因ではないと判明）
同じプロファイルに以下が写り込んでいた（ボタン1回の処理中）:

    9 calls  MACHIN3tools\handlers.py:562(depsgraph_update_post)
    9 calls  MACHIN3tools\utils\registration.py:14(get_prefs)
    9 calls  <frozen ntpath>:661(realpath)           ← ファイルシステムアクセス
    18 calls {built-in method nt._getfinalpathname}  ← 同上
    9 calls  rust_gpu_sdf_addon\handlers.py:1075(sdf_depsgraph_handler)
    9 calls  CAD_8_1_5_1\utils.py:1492(depsgraph_update_handler)

型紙ヘルパーがボタン1回で depsgraph 更新を9回発生させ、
そのたびに他アドオン3つのハンドラが全部呼ばれている。
MACHIN3tools は get_prefs() 内で realpath() を呼んでおり、
depsgraph更新のたびにファイルシステムアクセスが走る。

**新仮説 H-01:**
型紙ヘルパー側が対話操作中に depsgraph 更新を繰り返し発生させ、
他アドオンの重いハンドラが毎フレーム走ることで体感の重さが生まれている。

発生源:
- U-04 色変更 … _pattern_set_annotations → source_obj.data.update()（ADDON/__init__.py:3502）
                 _pattern_sync_live_seams → update_from_editmode() + data.update()
                 → カラーピッカーのマウス移動ごと
- U-03 G移動  … modalタイマー → bmesh.update_edit_mesh()（ADDON/__init__.py:4646）
                 → 0.12秒ごと、G移動中も継続

この仮説は観測と整合する:
- メッシュ規模に依存しない（Cylinderでも重い）… ○
- 対話操作で特に重い … ○
- 単発のボタン処理は速い（0.058秒）… ○
- 「軽いケースにまだ当たらない」＝環境が常に同じ … ○

型紙ヘルパー単体の問題ではなく他アドオンとの相互作用だが、
引き金を引いているのは型紙ヘルパー側（不要な update() の連発）なので
U-03 / U-04 の指摘自体は有効。

**次の検証:**
1. 計測スクリプト2_対話操作.py … 合印の色（重い）vs 矢印の色（軽い）を20回ずつ比較
2. MACHIN3tools / rust_gpu_sdf_addon / CAD_8_1_5_1 を一時無効化して同じ操作
3. blender.exe --factory-startup で型紙ヘルパーのみ有効にして比較

**知人への報告時の注意:**
「重い」とだけ伝えると環境差で再現しない可能性がある。
「他アドオンのdepsgraphハンドラと相互作用している」「不要なdata.update()が多い」
という形で伝えるべき。

### M-03. 【修正済み】パネルが存在しないオペレータを5つ呼んでいた
**日付:** 2026-09-18
**種別:** 不具合（重大）
**優先度:** 最高
**発見経緯:** ユーザがSystem Consoleにエラーが大量に流れているのを発見

**症状:**
System Console に以下が延々と流れ続ける。

    UILayout.operator(): unknown operator 'pattern_helper.start_notch'
    UILayout.operator(): unknown operator 'pattern_helper.clear_all_marks'
    UILayout.operator(): unknown operator 'pattern_helper.clear_corresponding_island'
    UILayout.operator(): unknown operator 'pattern_helper.clear_notches'

**調査結果:**
パネルが存在しないオペレータを5つ呼んでいる。
5つともファイル内のどこにも bl_idname 定義がない（未登録ですらなく完全に不在）。

  ADDON/__init__.py:11174  pattern_helper.clear_notches              「合印削除」
  ADDON/__init__.py:11181  pattern_helper.start_notch                「手動で合印を追加」
  （行不明）               pattern_helper.start_arrow                「手動で矢印を追加」
  ADDON/__init__.py:11310  pattern_helper.clear_all_marks            「すべてのマーキングをクリア」
  ADDON/__init__.py:11333  pattern_helper.clear_corresponding_island  「対応ハイライトをクリア」

**なぜ「重い」につながるか（H-03）:**
パネルが再描画される
  → UILayout.operator() が5回失敗
  → Blenderがエラーを5件レポート
  → コンソールへ書き込み（1件2行 = 10行）

Blenderのパネルは常時再描画される。
UIの上でマウスを動かすたび、_tag_redraw() が呼ばれるたび、depsgraph更新のたび。

Windowsのコンソール出力は同期的で非常に遅い。
特にコンソールウィンドウが表示されていると1行あたりミリ秒単位。
60fpsで再描画されれば毎秒600行の同期I/O。
メッシュ規模と完全に無関係に、あらゆる操作を重くする。

**すべての観測と一致する:**
- Cylinderでも重い … ○ メッシュ規模と無関係
- G移動・色ドラッグで特に重い … ○ 連続再描画が起きる操作
- スクリプト計測では速い（0.058秒 / 0.4ms）… ○ スクリプトはパネルを再描画しない
- 軽いケースに当たらない … ○ パネルが見えている限り常時発生
- コンソールを開いて調査していた … ○ 調査行為そのものが症状を悪化させていた

計測スクリプト1・2が「速い」と出たのは、
最もコストの高い経路（パネル再描画）を測っていなかったため。

**機能バグとしても重大:**
READMEに書かれている機能が動かない。
  「合印の長さ、太さ、色を調整できます。手動追加もできます。」
  「『対応ハイライトをクリア』で解除できます。」
これらのボタンは表示されるが押しても何も起きない。
ドキュメント記載の機能が5つ壊れている。優先度最高。

**関連: 登録漏れが常態化している**
定義はあるが classes に未登録のクラスが21個ある。
C-01の死にコード群（シーム作成系17個）に加えて:
  PATTERNHELPER_OT_cancel_pattern
  PATTERNHELPER_OT_confirm_pattern
  PATTERNHELPER_OT_place_text
  PATTERNHELPER_OT_set_text
後者4つはパネルからもコードからも呼ばれていないため実害はない。

なお内部の bpy.ops 呼び出し（confirm_flat_memo / edit_flat_memo /
rotate_flat_memo / unfold_real_mesh）はすべて登録済みオペレータなので、
実行時クラッシュはしない。被害はパネルの5ボタンに限定される。

**決定的な検証（各10秒）:**
1. Window > Toggle System Console でコンソールを閉じ、色ドラッグやG移動を試す
   → 明確に軽くなれば確定
2. Nキーでサイドパネルを閉じ、G移動を試す
   → パネルが描画されなければエラーも出ない → 軽くなれば確定

**知人への報告:**
これが最優先。「パネルから存在しないオペレータを5つ呼んでいる」の一行で伝わる。
パフォーマンス問題と機能バグの両方がこれ1つで説明できる可能性が高い。

### M-04. 【解決】移動が重い原因は描画キャッシュのキーに matrix_world が入っていたこと
**日付:** 2026-09-19
**種別:** 不具合（解決済み）
**関連:** U-02 / U-03 / U-04 / M-01 / M-02 / M-03

**症状:**
オブジェクトモードでGキー移動すると、マウスに追従せず、
数秒後に確定位置へ飛ぶ。メッシュ規模と無関係に発生する。

**原因:**
描画キャッシュ3つのキーに、型紙オブジェクトの matrix_world が
小数点以下7桁まで含まれていた。

    tuple(round(float(v), 7) for row in unfold_obj.matrix_world for v in row)

オブジェクトを動かすと matrix_world はマウス移動ごとに変わるため、
1フレームごとに必ずキャッシュミスし、以下が毎フレーム再計算されていた。

  _pattern_auto_flat_oriented_text_items  型紙IDの島内配置探索（v1.5.3）
  _pattern_auto_arrow_segments            矢印の島内安全配置探索（v1.5.4/1.5.5）
  _pattern_flat_colored_segments          合印などのセグメント生成

加えて _pattern_draw_cache に上限が無く、移動中は1フレームごとに
計算結果が積み上がり続けていた。

**なぜ切り分けに時間がかかったか:**
ビューを回すだけなら matrix_world は変わらないので、キャッシュが完璧に効く。
そのためビューポート描画の実測は 0.84ms/フレーム（195fps相当）という
健全な値を返した。「オブジェクトを動かしたときだけ」発症する形だった。

外れた仮説を順に記録しておく。いずれも実測で否定された。
  面数が主因                → 型紙作成は 0.058 秒
  他アドオンのdepsgraph干渉 → 1更新あたり 0.115〜0.468 ms、更新自体が数回
  コンソールへのエラー出力   → コンソールを閉じても改善せず
  描画ハンドラ自体が重い     → 0.84ms/フレーム
  メッシュが重い             → 514頂点

決め手になったのは「アドオンを無効化すると滑らかになる」という
最も単純な切り分けだった。これを最初にやるべきだった。

**修正:**
重い計算は matrix_world に依存しない（結果の座標へ掛けているだけ）。
計算をローカル空間で行ってキャッシュし、ワールド変換はキャッシュの外で
毎回掛けるようにした。
- 3つの compute 関数をローカル空間（_TS_IDENTITY）で計算
- ラッパーが _pattern_transform_rows で座標だけワールドへ移す
- _pattern_flat_notch_segments に matrix 引数を追加
- なめらか表示は逆行列でローカルへ戻してから揃える
- キャッシュに上限64件を設定

**教訓:**
キャッシュキーに「頻繁に変わるが計算結果に影響しない値」を入れると、
キャッシュが黙って無効化される。しかも特定の操作でしか露見しないため、
平均的な計測では健全に見える。

### M-05. 【誤り訂正】unregister のハンドラ外し忘れは存在しなかった
**日付:** 2026-09-19

一時「draft の unregister が depsgraph ハンドラを外していない」と判断したが、
これは誤りだった。remove_cleanup_handler() が両方を外しており、
unregister から呼ばれている。

アドオン無効化後のダンプにハンドラが残って見えたのは、こちらの計測
スクリプト（tools/measure_depsgraph.py）が元の関数をラッパーで
置き換えていたため。remove_cleanup_handler() は関数の同一性で判定するので、
ラッパーに置き換わっていると削除に失敗する。
さらにラッパーは __module__ と __name__ を元関数から引き継ぐため、
ダンプ上は本物と区別がつかなかった。

計測ツールが観測対象を汚染していた例。
ラッパーを仕込む計測は、対象の同一性に依存する処理（in 判定での削除など）を
壊しうることを念頭に置くこと。

### U-02. 「型紙を作成 / 更新」でフリーズすることがある
**日付:** 2026-09-18
**種別:** 不具合 / パフォーマンス
**優先度:** 高（主要機能が使えなくなる）

**症状:**
「型紙を作成 / 更新」を押すとBlenderが応答しなくなることがある。
発生するモデルとしないモデルがあり、メッシュ依存に見える。

**調査結果（コード読解）:**
無限ループは見つからなかった。while ループはすべて終了条件が保証されている
（シーム走査は処理済みエッジを毎回 unused から除去 / ADDON/__init__.py:3374、
Bresenham ADDON/__init__.py:1116、26進ラベル ADDON/__init__.py:6175 いずれも有界）。
よって「永久ハング」ではなく「終わるが極端に遅い」可能性が高い。

見かけ上フリーズする理由は、処理が同期的な execute() で一気に走るため
（PATTERNHELPER_OT_build_pattern / ADDON/__init__.py:4053）。
実行中はUIを返さないので「応答なし」になる。プログレス表示も中断手段もない。

**重い処理（実行順）:**
1. bpy.ops.uv.unwrap ANGLE_BASED / ADDON/__init__.py:3897 … 面数依存。最大の容疑者
2. 失敗時 CONFORMAL で再展開 / ADDON/__init__.py:3899 … 実質2回展開になる
3. _calc_real_scale 全ポリゴン走査 / ADDON/__init__.py:110 … 素のPythonループ
4. _build_flat_mesh 全ループ走査 / ADDON/__init__.py:144 … 素のPythonループ
5. _get_face_islands 連結成分探索 / ADDON/__init__.py:262 … 素のPythonループ
6. _pattern_refresh_auto_notches / ADDON/__init__.py:3333 … シーム本数・交差数依存

**「形」が効く部分:**
形状そのものより、形状が生む以下の要素が効くと思われる。
- シームの本数・交差（分岐）点の数 → 6のトレイル分割が増える
- アイランド数 → 5、および描画時のID/矢印の島内配置探索（v1.5.4追加・v1.5.5軽量化）
- シームが足りない閉じた領域 → 1が収束しにくく、最悪 RuntimeError → 2で倍の時間

**次にやる切り分け:**
1. Blenderをコンソール表示ONで起動し、固まった時に例外が出ているか無言かを確認
2. Decimateで面数を1/10にしシームはそのままで再実行 → 速くなるなら面数が主因
3. 面数そのままでシームを数本に減らして再実行 → 速くなるならシーム構成が主因
4. 5〜10分放置して完了するか確認

**知人への報告時:**
「面数◯◯、シーム◯本で◯分かかる／戻ってこない」と再現条件付きで伝える。
併せて、長時間処理に対する進捗表示・中断手段・面数の事前警告がない点も指摘できる。

### U-03. 型紙作成後、手動レイアウトのGキー移動が非常に重い
**日付:** 2026-09-18
**種別:** 不具合 / パフォーマンス
**優先度:** 高（手動レイアウトが実用にならない）
**関連:** U-02（ただし別原因。U-02は作成時、こちらは編集中）

**症状:**
型紙ができた後、「レイアウトの変更」でGキー移動するとすごく重く感じることがある。

**原因（特定済み）:**
UNFOLDHELPER_OT_layout_edit の modal が 0.12秒ごとのタイマーを仕掛け
（ADDON/__init__.py:4578）、毎ティックで型紙メッシュの全面をスキャンしている。

    selected_now = frozenset(f.index for f in bm.faces if f.select)   # :4615

変化の有無に関わらず毎秒約8回の全面Pythonループ。
10万面なら毎秒80万回。加えて
- ensure_lookup_table() も毎ティック（:4609）
- 選択変化を検出すると _last_selected 再構築でもう一度全面スキャン（:4657）

**Gキーで特に重い理由:**
modal が PASS_THROUGH を返すため、Blender標準のG移動中もタイマーが回り続ける。
ドラッグ中の再描画とPython全面スキャンが0.12秒おきに競合する。

作者はこの周辺を警戒しており、「update_edit_mesh を毎ティック呼ぶと
ネイティブtransformと喧嘩して島が動かなくなる」というコメントを残している（:4602付近）。
書き込み側は対策済みだが、読み取り側（全面スキャン）が残っている状態。

**マーキング停止は効いている:**
READMEの「手動調整中はマーキング表示を一時停止」は実際に機能している
（描画ハンドラ5か所で早期リターン / ADDON/__init__.py:8433, 8857, 9057, 9116, 11430）。
よって描画側は軽く、重さはこのタイマーが単独の原因と考えてよい。

**補足:**
except Exception: pass で全例外を握りつぶしている（:4661）。
毎ティック例外が出ていても無言なので、コンソールに何も出ない点に注意。

**確認方法:**
- 面数の少ない型紙で同じ操作 → 軽ければこのスキャンが原因で確定
- Escでmodalを抜けてから通常の編集モードでGを試す → 軽くなればほぼ確定
  （アイランド自動選択は効かなくなるので、面を全選択してから移動する）

**回避策:**
Escでmodalを抜け、手動で島を選択して移動する。

**知人への報告時:**
「10万面クラスでG移動が実用にならない／Escで抜けると軽い」と伝えれば
ピンポイントで直せるはず。

### U-04. マーキングの色などを変更すると非常に重い
**日付:** 2026-09-18
**種別:** 不具合 / パフォーマンス
**優先度:** 高（調整作業が実用にならない）
**関連:** U-02, U-03（「重い処理を毎回無条件に走らせる」同じパターン）

**症状:**
マーキングの色などを変えるとすごく重くなる。

**原因（特定済み）:**
色プロパティの update コールバックが2種類に分かれており、合印系だけが重い方を使っている。

重い方（_pattern_notch_setting_updated / ADDON/__init__.py:676）
- 合印の色     ADDON/__init__.py:11758
- 合印の長さ   ADDON/__init__.py:11798
- 合印の太さ   ADDON/__init__.py:11808
- 分割数       ADDON/__init__.py:11645

軽い方（_pattern_setting_updated / ADDON/__init__.py:672、キャッシュ無効化のみ）
- 数字の色     ADDON/__init__.py:11768
- 文字の色     ADDON/__init__.py:11778
- 矢印の色     ADDON/__init__.py:11788

_pattern_notch_setting_updated は合印モードがAUTOなら無条件に
_pattern_refresh_auto_notches を呼ぶ（ADDON/__init__.py:696）。中で毎回:
1. _pattern_sync_live_seams … bmesh同期 + data.update()
2. _pattern_seam_trails … 全エッジ走査でシーム隣接グラフ再構築 + トレイル全走査
3. 全トレイルの分割位置を再計算し、合印アノテーションを全件作り直し
4. _pattern_set_annotations … 全アノテーションをJSONシリアライズしてカスタムプロパティへ書き込み
5. キャッシュ無効化 → 次の再描画で型紙全体を再解析

カラーピッカーはドラッグ中のマウス移動ごとに update が発火するため、
1〜5が毎フレーム走る。

**設計意図とのズレ:**
コメントには「分割数の変更時に合印を即座に作り直すため」とある。
つまり再生成が必要なのは分割数だけなのに、ガードが「モードがAUTOか」しか見ておらず、
色や太さのような純粋な見た目変更でも同じ重い処理が走る。
長さは合印の形に影響するので再計算は要るが、
それでもドラッグ中に毎回JSON全書き出しをする必要はない。

**検証方法（決定打）:**
同じ型紙で「合印の色」と「矢印の色」を順にドラッグする。
- 合印の色だけ極端に重く矢印の色は軽い → 上記が原因で確定
- 両方同じくらい重い → 描画側の再解析が主因（別問題）
さらに合印方式を「なし」にしてから合印の色を触ると軽くなるはず
（mode != "AUTO" で早期リターン / ADDON/__init__.py:686）。

**回避策:**
- 合印方式を一旦「なし」にして色や太さを調整し、最後にAUTOへ戻す
- 色をドラッグではなく数値入力やスポイトで一発指定する（発火が1回で済む）

**知人への報告時:**
U-02 / U-03 と合わせ、「重い処理を毎回無条件に走らせている」という
共通パターンが3か所ある、と伝えると伝わりやすい。

### U-05. 自動レイアウトで用紙に入らない時、何もしてくれない
**日付:** 2026-09-18
**種別:** 機能要望 / UX
**優先度:** 中〜高（つまずきやすい導線）

**気づいた内容:**
「自動レイアウト」を押して用紙に入らなかった場合、
とりあえず指定用紙に全体が収まるよう動いてくれるとユーザフレンドリー。
平面化したものの縦横の最大寸に基づくシンプルな縮尺で十分に思える。

**現状の挙動:**
失敗時は全頂点を元座標に復元して CANCELLED を返す（ADDON/__init__.py:4620付近）。
画面上は何も起きない。メッセージも用紙寸法しか出ない。

  「210×297 mm の用紙にすべてのアイランドを収められませんでした」

展開図が実際何mmだったか、どれくらい足りないかが分からない。

なお PNG書き出し側のメッセージのほうが親切で両方出す（ADDON/__init__.py:5170）。

  「展開図 350.0×420.0 mm は A4 に収まりません。」

自動レイアウトのメッセージがこれに劣っているのは単に揃っていないだけに見える。
→ ここを揃えるだけでも改善になる。

**設計判断との衝突（要注意）:**
自動縮小はREADMEが明示的に否定している。
「型紙の実寸を優先するため、自動縮小は行いません」
コードにも _try_shelf_layout のdocstringに No scaling is ever applied.、
失敗箇所に # Hard failure: no scaling, no clipping. とある。意図的な設計判断。

理由は、縮尺された型紙と気づかず布を裁断すると材料が無駄になるため。
READMEが免責している「材料損失」そのもの。
よって「勝手に縮める」形だと作者は反対する可能性が高い。

**安全な形の案:**
A. 情報を出すだけ（主案・すぐ入れられる）
   「展開図 350×420 mm は A4(210×297) に収まりません。
     必要倍率 0.60 / A2 なら収まります」と出す。
   必要倍率は min(用紙W/展開図W, 用紙H/展開図H) で出せる。実寸は完全に保たれる。

B. 明示的な縮小プレビュー
   別ボタン「用紙に収めて確認（縮尺）」。
   縮尺率を型紙上とPNGに焼き込む（例「1/2 縮尺 ― 実寸ではありません」）。誤用を防げる。

C. タイル分割印刷
   実寸のまま複数ページに分割し貼り合わせマーク付きで出力。
   大きな型紙を実寸で出すための現実の定番解。実寸は完全に保たれるが実装は重い。
   要望としては別立てにするのが良い。

**実装上の注意（縮小する場合）:**
シェルフ詰めなので全体bboxは詰め方に依存する
（＝縮小すると詰め方が変わり必要倍率も変わる）循環がある。
単純にやるなら:
1. 全頂点を s 倍する
2. 既存の _try_shelf_layout をそのまま再実行
3. 失敗したら s を下げて数回リトライ（二分探索なら3〜4回で十分）
既存パッカーを使い回せるので実装は素直。

### U-06. 既知寸法による較正（ImageJ の Set Scale 相当）
**日付:** 2026-09-18
**種別:** 機能要望（重要）
**優先度:** 高（設計上の欠落を埋める本命機能）
**関連:** U-05（較正できれば「用紙に入るか」の判定も意味を持つ）

**要望内容:**
型を作るユーザは、部品のどこかの実寸に必ず意図を持っている。
選択した範囲（頂点・辺・連続辺）を「何cmにする」と指定できるようにし、
ImageJ の Set Scale のようにピクセル数と長さを後から紐づける考え方を導入したい。

**邪道ではない理由:**

1. README自身がこの穴を認めている
   「Scene Unit Scaleとモデルの実寸解釈そのものが制作時点から食い違っている
     データを自動判定・修正することはできません」
   現状は「そのシーンでBlenderが示している実寸を信じる」しかなく、
   前提が間違っていた場合の救済手段がゼロ。
   回避策ではなく、documented な設計上の欠落を正面から埋める機能。

2. スケールは幾何学から復元できない唯一の自由度
   形状データからは比率は分かっても絶対寸法は原理的に導けない。
   だから各分野が例外なく同じ解法に到達している:
   ImageJ Set Scale / フォトグラメトリのスケールバー /
   CADの参照距離スケール / 3Dスキャンの基準スケール物体。

3. ユーザはBlenderが持っていない情報を持っている
   「首周り38cm」「肩幅42cm」はモデル内に存在しない外部情報で、
   ユーザが入力する以外に入手経路がない。受け取る口がない現状のほうが不自然。

**実装上の要点（重要）:**

較正は「3Dモデル側」で行うべき。型紙（平面）側で行ってはいけない。

_calc_real_scale（ADDON/__init__.py:114）は全エッジの「3D長 ÷ UV長」比を集めて
中央値を取っている。

    ratios.append(world_len / uv_len)
    return median(ratios) if ratios else None

つまり平面化された型紙はすでに統計的フィッティング結果であり、
UV展開は等長写像ではないので辺ごとに比率がばらつく。
中央値を採る＝半分の辺は実際より長く半分は短い。
型紙上のどの1辺も、偶然を除いて3D上の実長と一致しない。

- NG: 型紙（平面）上で「この辺を20cmに」
      → その辺のローカルな歪みを全体に掛けてしまう。中央値フィットと喧嘩する
- OK: 元の3Dモデル上で「この辺／この稜線を20cmに」
      → 歪みの問題が起きない。実寸チェーンの上流を直すので以降すべて正しく追従する

**「範囲」は連続辺で測れる必要がある:**
首周りのような曲線は直線距離では測れず、エッジチェーンの合計長である必要がある。
その機構は既にある。
- _pattern_seam_trails（ADDON/__init__.py:3333）… 辺の連なりを歩く
- _pattern_trail_mark_positions（ADDON/__init__.py:3424）… 累積ワールド長を計算
合印を等間隔に置くためのコードだが、測定にそのまま転用できる。ゼロから作る話ではない。

**何を書き換えるか:**
Scene Unit Scale の書き換えは危険（シーン全体・他オブジェクト・物理演算に波及し、
「シーン設定は変更しません」という方針にも反する）。
型紙側に較正倍率を保持して mm 換算時に掛けるのが筋が良い。
非破壊で元モデルにもシーンにも触らず、既存の設計思想と一致する。

### U-07. UV展開の歪み率を表示する
**日付:** 2026-09-18
**種別:** 機能要望
**優先度:** 中（実装コストが極めて小さい割に有用）
**関連:** U-06

**内容:**
_calc_real_scale（ADDON/__init__.py:114）が全エッジの「3D長 ÷ UV長」比を
ratios リストに集めているが、中央値だけ使って残りを捨てている。
最大・最小も取れば歪み率を提示できる。

  「この型紙の伸び率: 最大 +8.2% / 最小 -5.1%（中央値基準）」

**なぜ有用か:**
型紙ユーザにとって歪みは実用的な情報。
歪みが大きい型紙は要注意であり、シームを追加すべきサインでもある。
READMEは「UV展開の性質上、誤差や歪みが生じる場合があります」と注意しているが、
実際にどれだけ歪んだかを知る手段を提供していない。
情報は既に計算されているのに捨てられている状態。数行で出せる。

### U-08. A4/A3への分割（タイル）印刷レイアウト
**日付:** 2026-09-18
**種別:** 機能要望（本命）
**優先度:** 高（「実寸が命」と「用紙に入らない」を両立させる唯一の正攻法）
**関連:** U-05（縮小案の上位互換。全体マップが U-05 の「縮小して全体を見たい」も満たす）

**要望内容:**
「これが実寸で正しい、でも用紙に入らない」で終わらせず、
A4やA3で分割したときの印刷レイアウトが出てくると強い。

**なぜ本命か:**
実寸を1mmも曲げずに、大きな型紙を家庭用プリンタで出せる唯一の方法。
作者の「実寸優先・自動縮小しない」という設計思想と全く衝突しない。むしろ思想を完遂する。
市販の型紙PDFは例外なくこの方式（A4タイル＋貼り合わせ）を採っている。

**必要な要素:**
- 貼り合わせ代（重ね代）… 10〜20mm程度の重複。裁ち落とし線・貼り合わせ線
- 合わせマーク … 三角やクロスの見当合わせ記号
- ページ番号 … 行列形式（A1, A2, B1, B2 …）
- 全体マップ … 縮小した全体図にページ分割グリッドを重ねた1枚。貼り合わせ順が分かる
- 基準四角（検寸スケール）… 重要。下記参照

**基準四角が重要な理由:**
家庭用プリンタは既定が「用紙に合わせる / Fit to page」で、黙って縮小する。
これに気づかず裁断すると、READMEが免責している材料損失がそのまま起きる。
各ページ（最低でも1ページ目）に 50×50mm の正方形を刷り込み、
「この四角が定規で50mmなら正しく印刷されています」と添える。
実寸主義を守るための実務的な必須要素であり、作者の思想に直接資する。

**実装の挿入点が極めてきれい:**
現状のPNG書き出し（UNFOLDHELPER_OT_export_png / ADDON/__init__.py:5122）は
- 用紙サイズから width_px / height_px を算出（ADDON/__init__.py:5176付近）
- 用紙1枚分のバッファを確保（ADDON/__init__.py:5185付近）
- ワールドmm → px を オフセットなしで直接マッピング

    x1 = x1_mm * px_per_mm
    y1 = height_px - (y1_mm * px_per_mm)

つまりページ原点のオフセットが存在しない。
タイル化は各描画箇所を

    x1 = (x1_mm - page_origin_x_mm) * px_per_mm
    y1 = height_px - ((y1_mm - page_origin_y_mm) * px_per_mm)

に変えて、ページ数ぶんループするだけ。描画ルーチン自体は一切変えなくてよい。

**副次的な利点:**
160,000,000ピクセル制限（ADDON/__init__.py:5180）が事実上不要になる。
巨大な1枚キャンバスを確保する必要がなくなり、
巨大カスタム用紙（U-05関連 / v1.5.6で追加）も本来は不要になる。
メモリ面でも現状より安全。

### U-09. 糊代の考慮
**日付:** 2026-09-18
**種別:** 機能要望
**関連:** U-08（分割印刷）

「糊代」は2つの意味に分かれる。文脈（「分割された型紙は」）からすると (1) だが、
(2) のほうが重い話なので併記する。

---

**(1) 貼り合わせ代 — 紙どうしを貼る**
優先度: 高（U-08に含める）

U-08 の「重ね代」と同じ。10〜20mmの重複＋合わせマーク＋裁ち落とし線。
技術的には簡単で、ページ原点をずらす際に重複分を差し引くだけ。

---

**(2) 縫い代・接着代 — 素材そのものに足す**
優先度: 中〜高（型紙アドオンとしての完成度を一段上げる中核機能）

READMEが明示的に除外している領域。
「縫い代、接着代、素材厚による補正なども自動では加味されません」

市販の型紙は必ず縫い代の有無を明記し、コスプレ造形でも接着代の有無で作り方が変わる。

**技術的には2Dポリゴンの外側オフセット。罠がある:**
- 凸角のスパイク … 鋭角を外側にオフセットすると角が無限に飛び出す。
  マイター制限または丸め／面取り処理が必要
- 凹角の自己交差 … 内側に食い込む部分でエッジが交差する。クリップ処理が必要
- 島どうしの衝突 … オフセット後は各島が太るので、島間隔が 2×縫い代 を超えていないと重なる。
  _pack_islands の間隔（既定10mm / ADDON/__init__.py:301）や
  _try_shelf_layout の5mm間隔と連動させる必要がある
- 辺ごとに違う … 実際の縫製では脇15mm・裾30mm・襟ぐり10mmと辺で変える。
  一律オフセットは簡略化にすぎない

**素材による違い:**
コスプレのEVAフォームでは突き合わせ接着なら縫い代ゼロ、
逆に素材厚のぶん外周を縮める必要すらある
（READMEが「素材厚による補正」を除外しているのはこの話）。
「一律N mm足す」だけでは足りず、用途の選択が要る。

**既にあるデータが使える:**
ADDON/__init__.py:6750 付近の by_source_edge は、
元のシームエッジごとにそこから生まれた型紙の境界辺を集めた辞書。
各要素が持つのは:
- island  … どの島の辺か
- mid     … 辺の中点
- inward  … 島の内側を向く法線

つまり境界辺それぞれについて「どの島とつながる辺か」と「外向き方向」が
すでに計算済み。

- 縫い代のオフセット → inward を反転すれば外向きベクトルがそのまま得られる
- ペーパークラフト的な糊しろタブ → 接合する2辺のペアが分かるので、
  タブを片側だけに付ける判断ができる（両側に付けると重なって貼れない）

接続先ID表示のために作られたデータだが、そのまま糊代生成の基盤になる。
U-01 / U-06 / U-07 と同じ「既にあるものを使う」パターン。

**出力時に適用するべき:**
型紙メッシュ本体は実寸のまま保ち、PNG書き出し時にオフセット線を追加で描く。
- 実線 = 裁断線（縫い代込みの外周）
- 破線 = 縫い線 / 合わせ線（実寸の元外周）
市販型紙の標準表記であり、非破壊だからON/OFFも切り替えられ、
既存の「元モデルを変更しない」設計とも一致する。

**登録漏れを構造的に潰す（最優先）:**
classes タプルの手書きをやめ、イントロスペクションで収集する。

    def _iter_classes():
        for module in (ops_model, ops_marking, ops_layout, ops_export, ui_panel):
            for obj in vars(module).values():
                if (isinstance(obj, type)
                        and issubclass(obj, (bpy.types.Operator, bpy.types.Panel))
                        and getattr(obj, "bl_idname", None)):
                    yield obj

これで C-01（21個の未登録）は二度と起きない。定義した時点で自動登録される。

M-03（実在しないオペレータ）には開発時チェックを追加:

    def _self_check():
        for idname in PANEL_OPERATOR_IDNAMES:
            group, _, name = idname.partition(".")
            if not hasattr(getattr(bpy.ops, group), name):
                print(f"[型紙ヘルパー] 警告: オペレータ {idname} が存在しません")

**段階的にやるべき（重要）:**
12,000行・グローバル14個・状態4系統を一気に分割するのは危険。
個人プロジェクトなら尚更、「動いていたものが動かなくなる」リスクが最大のコスト。
依存の少ない葉から順に抜き出すのが現実的。

## C-05 分割の完了と、その過程で見つかったもの（2026-09-20）

C-03 で提案した段階的分割を完了した。提案とは1点違えた。

**登録の自動化（当時の推奨 4番）は採用しなかった。** イントロスペクションで
集めると「定義した時点で自動登録」になるが、登録の順番が読めなくなる。
パネルはオペレータより後でなければならず、暗黙の順序に依存する形は避けた。
各モジュールが自分の `classes` を持ち、`ops/__init__.py` が並べる形にしてある。
一覧が目に見えるので、検査ツールも読める。

結果:

    unfold/__init__.py   12,708 → 216 行
    draft/__init__.py     5,380 → 160 行

### 分割そのものより、検査ツールの方が成果が大きかった

分割中に `tools/check_addon.py` が拾った不具合。いずれも**押すまで分からない**
種類で、人の目では通り抜ける。

| 内容 | 件数 | 現れ方 |
|---|---|---|
| 未定義のまま読まれている名前 | 約40 | 描画やハンドラの中で握り潰され、黙って出ない |
| ローカル変数が同名の関数を隠す | 1 | 「シームを入れる」が落ちる（利用者まで届いた） |
| `@persistent` の欠落 | 2 | 保存して開き直すと効かない |

3つとも検査項目として残した（8・9・10番）。

**検査ツール自体を5回直した。** 分割が進むと前提が変わり、誤検出が出る。
誤検出を放置するとツールの出力が読まれなくなり、本物が埋もれる。
直すのを後回しにしないこと。

### 分割中に直した実害のある不具合

| 内容 | 原因 |
|---|---|
| 島ハイライトと配置の下描きが出ない | 描画を移したとき、状態への参照を取り残した（自分のミス） |
| 「シームを入れる」が落ちる | 関数名を短くしすぎ、ローカル変数と衝突（自分のミス） |
| 手動レイアウト中のフラグが解除されない | 初期化キーの一覧と、実際の処理が二重管理で食い違っていた |
| 初期化が1回しか走らない | `_tsunfold_reset_overlays_on_load` に `@persistent` が無い（元から） |
| 三面図の視点合わせが静かに失敗 | `Vector` が一部の関数でのみ import されていた（元から） |

前2つは自分が持ち込んだもので、どちらも**テストが無い経路**だった。
実機確認に頼ると、操作の最中にしか現れないものは見逃す。

### U-04（色変更が重い）の決着

種類ごとの色設定を全てキャッシュキーへ入れ、更新を再描画だけに変えた。
これまでは色を変えるたびに epoch が進み、島の解析と配置探索が
まとめて作り直されていた。

同時に、手動で置いた印が色設定に追従しない問題も直した。置いた時点の色を
保存して描画に使っていたためで、オート合印と矢印だけが追従していた。
同じパネルの中で挙動が食い違っていたことになる。

印ごとに色を変えるUIは元々存在せず、保存値は置いた瞬間の設定の写しでしか
なかった。描くときに設定から引く形へ変えた。

## C-07 縫い代が別の島の面を混ぜていた（2026-09-22）

`export/allowance._build` が、`geometry.face_islands`（**頂点番号**を返す）の結果を
`island_loops(mesh, face_indices)` へ**面番号**として渡していた。

島が1面ずつなら偶然合う。立方体の展開でもたまたま合っていたので、既存のテストは
通っていた。2×2 の島を3つ並べると、3つ目の島に**内側を横切る裁断線**ができる
（正しくは 24 本のところ 28 本）。刷れば、切ったときに型紙が割れる。

面番号を返す `geometry.face_island_polys` を足し、`face_islands` はそれを使って
頂点番号へ直す形にした。島を探す処理は1つのまま。
回帰テストは `test_seam_allowance_follows_each_island`。

### 同じ型の取り違えは型を見ても分からない

どちらも `list[list[int]]` で、名前も `face_islands` と `face_indices`。
**名前に「face」と入っているのに中身は頂点**、という関数が元凶。

## C-08 並べるときに、縫い代のぶんを空けていなかった（2026-09-22）

並べる処理（`pack_for_pages`・`try_shelf_layout`・`pack_islands`）は、
どれも型紙の輪郭の外接矩形だけで詰めていた。縫い代・糊代は輪郭の外へ出るので、
**既定の縫い代 10mm・間隔 10mm で、隣の島の裁断線が 14mm 重なっていた。**

10mm ではなく 14mm なのは、角でマイターが伸びるため。縫い代は鋭い角で幅の
最大 2.5 倍まで出る。幅で見積もると足りない。

`allowance.island_reach` が島ごとに実際にずらして出幅を測り、
`build.layout_islands` がそれを添えて並べる側へ渡す。三つとも同じものを使う。
回帰テストは `test_layout_leaves_room_for_the_seam_allowance`。

### 残したもの

- **代をあとから入れても並べ直さない。** 手で並べたかどうかの記録が無く
  （`MANUAL_LAYOUT_ACTIVE` はドラッグ中だけ立つ）、自動で並べ直すと手で
  並べた配置を黙って崩す。パネルに「押し直すと重ならない」と出すだけにした。
- `collect.pattern_bounds` は今も「幅のぶんだけ四方へ広げる」見積もり。
  鋭い角のある型紙では、用紙ガイドが実際より小さく出うる。`island_reach` へ
  寄せるなら、毎フレーム呼ばれるのでキャッシュが要る。
- 間隔のスライダーは `pack_islands`（横一列）を呼ぶ。型紙を作った直後の並び
  （用紙に沿う）と違い、動かすと用紙に沿った並びが崩れる。
